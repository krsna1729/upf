# Compliance: what is implemented, and what proves it

Status: 2026-10-17. `compliance-landscape.md` is about the field (who else
implements what, and with what evidence); this file is about us: one row per
capability, its clause, its state, and the test or script that shows it.
"Interop: none" means only our own stand-ins have driven it — no open-source SMF
has yet, so no row claims it.

Every clause number here was read off **ETSI TS 129 244 V17.9.0 (2023-07)**, the
PDF ETSI publishes, on 2026-10-17: the grouped IEs (PDR, PDI, FAR, QER, URR,
BAR, MAR) are specified inside the procedure clauses (§7.5.2.x for establishment,
§7.5.4.x for modification), and §8.2 holds the IEs they are built from. An
earlier revision of this file cited clause numbers from memory; most were wrong,
which is why the version is named.

## Declared capabilities (TS 29.244 8.2.25)

The Association Setup Response advertises **two optional UP Function Features**:
FTUP, and only in the run that has a session layer (`upfd -bess`), because that
is where the F-TEID allocation lives; and EMPU, and only in the run whose graph
carries an End Marker out (`upfd -end-marker`), because that is where the
construction lives (TS 29.244 5.3.2: a UP function that constructs them "shall
indicate so to the CP function by setting the EMPU flag"). With no session
layer this node refuses every session request, so an answer promising an F-TEID
it could not allocate would be a claim with nothing behind it; with no
end-marker port it could construct no marker, and the bit stays clear.
Everything else the four octets could say stays clear: every other optional
feature is still a milestone of its own, and the answer otherwise declares
mandatory behaviour alone.

What the FTUP bit covers (TS 29.244 8.2.3), and what proves it:

| part of the feature | state | evidence |
|---|---|---|

Two design choices 8.2.3 does not settle, recorded here because the section
leaves them to the implementation:

- **The group is the session's, not the message's.** The section requires the
  sharing of "the PDRs requested to be created in a PFCP Session Establishment
  Request or PFCP Session Modification Request with the same CHOOSE ID value",
  i.e. within one message. This UPF carries the CHOOSE ID for the session's
  life, so a PDI a later modification creates with an ID the session has
  already used is given the same F-TEID: that is what makes the ID a handle an
  SMF can program against across requests, and a group whose value changed per
  message would be no group at all. An entry is dropped, and its TEID released,
  as soon as no PDR of the session names it.
- **Two CHOOSE IDs are two F-TEIDs.** Nothing in the section makes two values
  one tunnel, and an SMF that used two IDs to ask for two tunnel endpoints
  would be given one by an implementation that answered every CHOOSE request
  with its single F-TEID.

One optional behaviour is implemented without being declared:

| bit | implemented where | why the bit is still off |
|---|---|---|
| UEIP | the UE IP IE is a rule key and the session's UE address (`internal/session/compile.go`) | the bit covers the CHV4/CHV6 half too -- the SMF asking the **UP** to choose the address -- and this UP does not allocate one: such a request is refused with a rule failure (`TestAUEIPAllocationRequestIsRefused`), so the feature is half there and the bit stays off until allocation exists |

A milestone that implements a feature turns its bit on in `cmd/upfd`; a feature
whose bit is on with nothing behind it is the kind of claim
`compliance-landscape.md` collected from other projects.

## Profiles: what each row means in each profile

the firewall module — and **custom** — this tree's keyed per-session matcher

precedence order). Every row above is written for the generic profile; this

the rest: **a row not named here holds in both profiles**, because it is
control-side (the N4 layer, the session store, the reporting path, the routing

### The performance difference, as far as it is measured

Capability is not the only axis: the profiles differ in what a session change
costs and what a packet costs. Nothing below benchmarks the custom path yet —
its uplink arm (`ci/pdrmatch-path.sh`) has run, and checks correctness, not cost — so each row says whether it is **measured**, **derived**
from measured rows, or **owed**.

| axis | generic — wildcard | generic — firewall | custom — keyed | status |
|---|---|---|---|---|
| one session change | rebuild the shard: ~44–50 µs at 1K rules, ~1 ms at 10K | rewrite the whole policy: O(all rules) | one upsert of that session's rules: O(its rules) | wildcard measured (published row); firewall derived; keyed owed |
| one packet | one masked-tuple lookup in a table every session shares | an **indexed** lookup over the whole policy (the stock module builds `FirewallTable`; the scan is the custom path's matcher, not this one) | the session selector (an LPM lookup) plus a 2–4 rule scan | the indexed rows are measured — 114 M keys/s at 10 rules hitting the first, 34 M/s at 1,000 spread, 26 M/s over IPv6 — and the 117 M/s *scanned* row at 10 rules belongs to the custom path's matcher; the selector-plus-scan row is owed |
| memory per session | per-rule and per-group in the shared table | per-rule in the policy | one map entry plus one rule vector | owed (BESS's per-rule/per-group rows are being measured) |
| the 1M-session target | the rebuild makes it infeasible (tens of ms per change) | the whole-policy rewrite is worse | the shape it was built for | derived from the rows above |

Two cautions that travel with these numbers. **The crossover moves with the
deployment**: it exists only for deployments that change rules at all, and the
selector's memory moves by an order of magnitude with the address plan, so any
published line needs its shape attached. And **the comparison covers only what
both can compile** — the timing corpus is the intersection (IPv4,
mask-expressible ports), because the custom path refuses a QFI-naming PDI and a
BUFF PDR; a timing run must therefore never be read as "the generic path is
fine" where the custom path simply cannot take the rule.

## Gaps, in the order they close

1. **URR** (7.5.2.4 + the Session Report path): volume and time per URR,
   thresholds and quota, reported so a real SMF accepts it. The counters are the
   design's differentiator and the one place the field is weakest.
2. **End marker and echo** (GTP-U v1, 7.4.2 and TS 29.281): closed on
   2026-10-17. The `gtpu_responder` module answers an Echo Request as 7.2.2
   prescribes, and a modification whose SNDEM flag moves a FAR's F-TEID makes
   `upfd` construct the End Marker itself -- old TEID, old peer, the UPF's N3
   address as the source -- and write it into the graph's `unix_port`, which
   carries it to the N3 output after the switch has landed.
3. **DSCP copy and marking**: closed. The copy is in as of 2026-10-17 (the encap
   writes the inner TOS on the outer header), and the SMF's override is in as of
   2026-10-18. The doc used to call that "the per-QER override the SMF can ask
   for with the QoS rules"; the IE the SMF actually uses is the FAR's
   **Transport Level Marking** (8.2.12, procedure 5.4.13 -- in a FAR's
   forwarding parameters, not a QER), and it is what is now read: the IE's two
   octets are carried into the session's tunnel record, where the encap marks
   the outer IPv4 header with its DSCP and keeps the bits its mask names -- the
   ECN bits, with the spec's 0xFC -- from the inner packet.
   TestAFARsTransportLevelMarkingReachesTheTunnelRecord proves the compiler half
   and `ci/smoke-gtpu.sh` the datapath half (a record marked 0xb8fc over an
   inner TOS 0x02 leaves the outer TOS 0xba and its checksum). The row also used
   to carry an apology for the uplink, and it should not: the clause marks the
   **transport** header -- TS 23.501 5.8.2.7, the clause the FAR's table
   (7.5.2.3-2) cites for the value, says "the DSCP in the outer IP header", and
   TS 29.244 5.4.13 marks "traffic at the UPF/MB-UPF" on the transport of the
   packets -- so an uplink FAR whose packet leaves with no outer header (to N6)
   asks for nothing, and marking the subscriber's own DSCP there would be a
   defect rather than the missing half; on the uplink the access-side marking is
   the (R)AN's (TS 23.501 5.7.1.7: "(R)AN performs transport level packet
   marking in the UL"). The clause's own uplink case is a FAR with Outer Header
   Creation toward a peer UPF (N9), where the UP *does* write the outer header:
   that takes the same tunnel record and the same encap (the record's `marking`
   is written from the FAR wherever a direction names a tunnel resource), and
   this deployment names one for the downlink only, because it serves N3 and N6
   and no N9 -- a graph statement, not a missing mechanism. The other mechanism
   the old wording blurred into this one is the QER's **DL Flow Level Marking**
   (8.2.66, procedure 5.4.5): that is the off-path TDF's application detection
   (an ADC rule's DSCP, and where a tunnel is used there the DSCP for SDF
   detection "shall be carried in the inner IP header" -- the opposite header
   from transport level marking), so it is not "the same override reached from
   the QoS rules" and a 5GC UPF owes it no more than it owes a TDF.
4. **BAR + DDN** (7.5.2.6 + 7.5.8.2): closed on 2026-10-17 for a graph that
   carries the buffering branch (`deploy/buffer-path.yaml`; `deploy/upf.yaml`
   gains it once the deployed daemon carries BESS's `key_attrs`, which the
   store's key needs). The one deviation left in the row over 8.2.26 is the DDN
   trigger being a poll at `-urr-interval`; the SMF's per-BAR numbers now reach
   the store's per-flow `flows` entry (8.2.29, 8.2.30), written by the compiler
   in the session's own transaction and erased with the episode, so a flow's
   cap and timeout are the SMF's rather than the graph's. The duration's expiry
   is measured live as of 2026-10-18, and its free is *silent* (the sweep calls
   `bess::PacketFree`: no gate, no metric, and `GetDesc` is not served here), so
   what the arm observes is the absence of the effect the timeout would
   otherwise leave: `TestLiveSessionHoldsNothingAfterTheBufferingDurationPasses`
   waits out a 2 s duration, then sends the Update FAR that releases in
   `TestLiveSessionBuffersAndReleasesTheHeldPackets`, and the encap does not
   move -- the flow was freed before the instruction arrived. The differential
   is the entry: without `timeout_ns` the module-wide `timeout_ms` (5000) would
   still hold the flow at that moment and the instruction would release it (the
   run with the write suppressed fails with `the encap carried 16 packets after
   the instruction (was 0)`), and the 3 s wait is deliberately under that 5 s.
   This needs a daemon carrying BESS 0bfd2783 -- the bounded per-run sweep
   (`EvictExpiredBounded`, 256 flows a run), without which the timeout is only
   checked under global `max_packets` pressure.
5. **QFI and Network Instance** (8.2.89, 8.2.4): the Network Instance is read
   and resolved now (row 8.2.4 above, `internal/routing`, `upfd -instances`),
   and so is the QFI: a PDI's QFI is the uplink rule's last key field, where
   the graph declares it, so a PDR told apart from another only by its QoS flow
   is a rule of its own instead of a refusal; a QER's QFI goes into the tunnel
   record, where the encap writes the downlink packet's PDU Session Container
   from. The vif half of this gap is in: the port's three interfaces each write
   their route domain, so a downlink rule's key on a port says which one the
   packet arrived on and the rule is selected by it (`deploy/veth-port.yaml`,
   `ci/veth-port.sh`, docs/ports.md). What remains is the placement
   measurement -- the per-pattern RSS and the line rate a NIC's RSS engine is
   needed for (docs/design.md's port section, and the roadmap's hardware
   list).
6. **IPv6** — refused on the WildcardMatch path, not silently: a PDI naming an
   IPv6 UE address or SDF prefix is answered cause 73, because the classifier's
   four bytes cannot carry it and widening it would match other sessions'
   packets (TestANonIPv4PDIIsRefusedNotWidened), and an F-TEID IE asking for an
   IPv6 address (CH with V6 and no V4) is refused for the same reason
   (TestACHOOSEForIPv6IsRefused), which is also why the FTUP bit above cannot
   promise an IPv6 F-TEID. What moved on 2026-10-18: an **SDF filter's IPv6
   prefix** now compiles instead of being refused, on the opt-in firewall path,
   whose table holds IPv4 and IPv6 rules in one policy and whose rules carry a
   prefix as a CIDR string with its length
   (TestAnIPv6SDFPrefixCompilesOnTheFirewallPathOnly; the underlying BESS work
   is D-147 in that tree). Three things that move is not: the refusal stands
   wherever the WildcardMatch path is configured, which is every graph a
   deployment can run today; the PDI's own IPv6 *UE address* is still refused,
   because the F-TEID key, the tunnel record and the WildcardMatch key's
   address fields are IPv4-only, so an IPv6 prefix in a filter is not an IPv6
   session; and the path is **armed only through the session lane**: the rule
   now names its PDR's ActionId, and `FIREWALL=1 ci/session-path.sh` runs the
   whole lane (counters, quota, DSCP, End Marker) through the stock `firewall`
   module on `deploy/firewall-path.yaml` -- with the compiler before that
   change the four traffic tests fail, after it they pass. It is the
   5-tuple and the ActionId that are shown; no arm yet sends a port range or an
   IPv6 packet through it. (The stage built from this repo's BESS copy does
   load `Firewall`; the earlier note that it did not is stale.) The rest of this gap
   therefore stands as it was: the dataplane's tables, the two address fields
   and the TEID rule key would all need a second form, and this is what "IPv6
   not implemented" means here.

(Gap 1 — URR — is closed on our side as of 2026-10-17: the counters, the
decision and the report are in and tested, and gap 2 below is what the SMF
sees next. Its interop half is partly in: free5GC completed the release that
answered with termination reports in the Session Deletion Response (2026-10-18,
`ci/interop/run.sh`; that it read them is not shown); a periodic or threshold
Session Report Request has not been seen by a real SMF — see "Interop".)

(Gap 7 — FTUP's CHID — closed on 2026-10-17: the compiler reads the F-TEID's
CH and CHID flags, the session keeps one F-TEID per CHOOSE ID, and `upfd`
advertises FTUP where the session layer runs. See "Declared capabilities"
above for what proves it.)
